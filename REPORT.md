# OS Resource Manager: Project Report

## 1. Abstract

OS Resource Manager is an integrated, menu-driven simulator for selected operating-system resource policies. It implements CPU scheduling, variable-size memory allocation, Banker's safety analysis, and disk scheduling in reusable Python modules. A Bash launcher prepares runtime directories and can invoke the automated test suite. For consistent comparison, a unified reporting module uses shared CSV sample workloads and exports metric tables, a text analysis, and optional labelled graphs. Unit tests cover algorithm outputs and important invalid and boundary inputs.

## 2. Introduction

An operating system allocates processor time, memory, and storage access among competing workloads. Policies make different trade-offs: a scheduler can reduce average waiting for one workload while delaying another process; a memory fit strategy can affect whether later processes fit; and disk ordering affects mechanical head travel in the modeled device. This project makes these effects observable through deterministic inputs and measurable outputs.

## 3. Problem Statement

Students often encounter resource-management algorithms as isolated exercises. Without a common interface, shared datasets, and consistent metrics, it is difficult to compare policy behavior or test invalid input. This project integrates the algorithms in one terminal application, validates their input contracts, and provides repeatable comparisons and exports.

## 4. Objectives

- Implement FCFS, SJF, Round Robin, and Priority CPU scheduling.
- Implement First Fit, Best Fit, and Worst Fit memory allocation.
- Determine safe and unsafe states using Banker's safety algorithm.
- Implement FCFS, SSTF, SCAN, and C-SCAN disk scheduling.
- Calculate and compare policy-specific metrics using identical per-module datasets.
- Provide timestamped activity logs, automated tests, CSV reports, and visualizations.
- Support Python execution on Windows and Bash execution on Linux, macOS, WSL, and Git Bash.

## 5. Scope

The program models algorithms; it does not inspect or control the host machine's actual CPU, memory, processes, or disks. CPU SJF and Priority are non-preemptive. Memory blocks are variable-size and allocations consume a block's remaining free capacity. Banker's analysis checks whether all supplied processes can finish from the current state. Disk SCAN/C-SCAN include endpoint travel according to the selected direction.

## 6. Literature Review

The implemented policies are standard operating-systems teaching topics. FCFS is a simple arrival-order baseline. SJF prioritizes shorter available bursts and can reduce average waiting for known burst lengths. Round Robin assigns bounded CPU quanta to ready processes. Priority scheduling selects the highest-priority ready process and can starve lower-priority work without aging. Fit algorithms choose a free region according to size; Banker's algorithm uses maximum claims to test safe completion order; and disk algorithms reorder requests to reduce movement. Their behavior is workload-dependent, which motivates comparison on a common input set.

## 7. System Architecture

`main.py` owns the integrated menu and delegates to the module interfaces. `modules/common.py` provides shared console input, logging, and paths. Each resource domain owns its algorithm calculations and interactive menu. `modules/reporting.py` loads the sample data, invokes the same public algorithm functions as the interactive menus, prints comparisons, and writes artifacts under `reports/`. `run.sh` creates runtime directories, checks the Python version, launches the program, and supports a test mode.

Data structures are plain Python dictionaries for process records and result rows, lists for vectors, matrices, ready queues, and timelines, and tuples for CPU timeline segments. CSV files are used for durable sample inputs and exports.

## 8. Methodology

Each algorithm is implemented as a reusable function that accepts data and returns structured results. Interactive menu code handles prompting and display separately. Validation occurs at the function boundary so callers and automated tests receive predictable `ValueError` exceptions. The reporting path loads one dataset per domain and passes it unchanged through every policy in that domain. Tests verify known metrics and invalid-input behavior; sample comparison outputs are generated by executing the application code rather than hand-entered.

## 9. Algorithm Explanations

### CPU Scheduling

- **FCFS:** Processes execute in arrival order; idle intervals are recorded when the ready set is empty.
- **SJF:** Among arrived processes, select the smallest burst; execution is non-preemptive.
- **Round Robin:** A FIFO ready queue runs each process for at most the positive time quantum and requeues unfinished work.
- **Priority:** Among arrived processes, select the smallest numeric priority; execution is non-preemptive.
- **Metrics:** `CT` is finish time, `TAT = CT - arrival`, and `WT = TAT - burst`. Averages are arithmetic means across processes.

### Memory Management

Each process is assigned to the first suitable remaining region (First Fit), the smallest suitable region (Best Fit), or the largest suitable region (Worst Fit). The allocation reduces that region's free space. Utilization is allocated process memory divided by total block capacity, expressed as a percentage. Unallocated processes remain explicitly marked.

### Deadlock Management

Need is calculated element-wise as `Maximum - Allocation`. Starting from Available, the safety procedure repeatedly finds an unfinished process whose Need is no greater than Work, then adds its Allocation back to Work. If all processes finish, their order is a safe sequence; otherwise the state is unsafe. Inputs with negative values, mismatched dimensions, or allocation above maximum demand are rejected.

### Disk Scheduling

FCFS preserves request order. SSTF repeatedly selects the nearest pending cylinder. SCAN services in one direction, reaches the disk boundary, and reverses. C-SCAN services in one direction, wraps at the opposite boundary, and continues. Total movement is the sum of absolute changes between consecutive head positions; average movement is total divided by request count.

## 10. Implementation

The codebase uses Python standard-library features for algorithms, CSV access, logging, and report generation. Matplotlib is an optional dependency for PNG charts. `run.sh` is the Bash integration point; PowerShell can invoke `main.py` and unittest directly. The six-option main menu connects all four resource modules, performance reports, and application exit.

## 11. Results and Analysis

The checked-in sample CPU workload contains four processes. Running the reporting module produces average waiting times of FCFS 4.75, SJF 4.00, Priority 4.25, and Round Robin 7.00 time units; SJF is lowest on this dataset. Memory utilization is First Fit 43.59%, Best Fit 68.65%, and Worst Fit 43.59%; Best Fit allocates all four sample processes. Disk movement is FCFS 642, SSTF 208, SCAN 332, and C-SCAN 391 cylinders; SSTF is lowest for the supplied queue and initial head. These results illustrate this workload only and do not establish a universally best policy.

The report menu writes one CSV comparison per domain and a plain-text summary. If Matplotlib is installed, CPU metric and Gantt charts, memory allocation and utilization charts, and disk head movement charts are also written to `reports/`.

## 12. Testing

The project uses `unittest` and runs with `python -m unittest discover -s tests -v` or `./run.sh --test`. The suite covers FCFS waiting-time calculation, Round Robin completion, idle CPU intervals, duplicate process IDs, and zero burst rejection; memory Best Fit, invalid strategies, and unallocated processes; Banker's safe/unsafe cases, negative resources, and allocation above maximum; disk FCFS movement, invalid disk size/direction, and out-of-range cylinders; and all algorithm families in common-dataset comparisons. The suite passes in the development environment.

## 13. Limitations

The application has a terminal interface rather than a graphical dashboard. SJF and Priority are non-preemptive and use supplied burst/priority values. No starvation aging is modeled. Memory fragmentation is represented only by remaining space in variable-size regions; paging and compaction are outside scope. The safety module does not model dynamic resource requests. SCAN movement assumes the disk head travels to an endpoint where the policy requires it. Graph generation requires Matplotlib.

## 14. Future Scope

Potential extensions include preemptive SJF and Priority, aging, paging and page-replacement algorithms, dynamic Banker's requests, configurable workload entry for report comparisons, richer fragmentation metrics, and a cross-platform graphical dashboard. A future dashboard should call the same algorithm functions to avoid duplicating policy logic.

## 15. Conclusion

The project integrates core OS resource-management examples behind a consistent Python interface and an optional Bash automation layer. Structured algorithm outputs support interactive display, regression tests, reproducible cross-policy metrics, and report generation. The sample results demonstrate why algorithm performance should be interpreted in the context of a particular workload.
